**Tracy profiling covers the whole application and can be switched on at run time in a release build.** Zones cover the engine and every transport, the studio service, the CLI, the GUI (every event the application dispatches with its receiver and type, painting, the event loop, panes, dialogs, layout and link routing), the test runners (one zone per test) and new per-component benchmarks in `vss_perf`, with plots for rates and queue depths and markers for state changes. In a Release build with `VSS_TRACY=ON` the instrumentation is compiled in but dormant: Tracy is built with a manual lifetime, so there is no profiler thread, socket or buffer, and a zone costs one relaxed load, until profiling is turned on with `--profile` (GUI, CLI, `vss_perf`), `VSS_PROFILE=1`, or Settings, Performance, Profiling in the GUI, which also shows the state in the status bar and About. The listener is bound to 127.0.0.1 unless `--profile-remote` is given, never broadcasts, and sends nothing until a profiler connects; Debug builds still start by themselves. Turning it off pauses recording at once, but Tracy cannot close its socket before the program exits. `vss_perf` reports the cost of a zone while dormant, armed and recording, `perf/floors.json` accepts a `max` limit, `tools/tracy_report.py` groups a capture by area and checks the zones a workload must produce, and new presets `linux-tracy-gui` and `windows-msvc-tracy-gui` build a Release GUI with the profiler compiled in.

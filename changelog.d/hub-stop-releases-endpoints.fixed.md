**Stopping a hub releases its endpoints.** `hub::stop()` let go of the io_context's work guard before it posted the shutdown handlers, and it stopped the io_context at once when no live endpoint was left, so the shutdowns that `remove_endpoint()` had queued were discarded. An endpoint with a parked read then kept itself alive through its transport after the hub was gone, which AddressSanitizer reported as a leak in the unit tests that use a loopback port. The work guard now stays until `join()`, the hub counts the shutdowns in flight, and the io_context stops only when `stop()` has been called and none are left. Two tests check that destroying the hub frees an idle endpoint and one that was just removed. The loopback transport also stops relying on a moved-from `std::function` being empty, which libc++ does not guarantee for a small callable, so on macOS the parked read stayed in place and a second write could complete it again.

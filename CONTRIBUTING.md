# Contributing

## Building and testing

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug \
  -DVSS_BOOST_ROOT=/path/to/boost \
  -DVSS_VIRTUAL_SERIAL_DIR=/path/to/boostasio-virtualserial
cmake --build build
ctest --test-dir build --output-on-failure
```

Boost.VirtualSerial is consumed as a custom library, not as a Boost release.
Point `VSS_VIRTUAL_SERIAL_DIR` at a checkout; the sibling directory is used
automatically when it exists.

## Before opening a pull request

1. `ctest` passes, including the GUI self-test when Qt is available.
2. New behaviour has a test. The suites are the specification; a bug fix should
   fail before the fix and pass after it.
3. Coverage stays above the gates (`VSS_COVERAGE=ON`, then
   `tools/coverage_report.py --min-lines 90 --min-branches 80`).
4. Performance floors still hold (`vss_perf`, `tools/perf_report.py`).
5. The change has a fragment in `changelog.d/` (see below).
6. The build is clean with `-DVSS_WARNINGS_AS_ERRORS=ON`.

## Commit and pull request text

Commit messages, pull request titles and bodies, and committed files must not
carry:

* a trailer other than a human `Signed-off-by`;
* a "generated by" or "generated with" statement;
* AI or tool attribution of any kind.

A final paragraph made only of `Word: value` lines is read as trailers. To end a
body with such a line, put a sentence after it. The rule covers pull request
bodies because the squash merge uses the body as the commit message.

The `Commit text` CI job runs `check_text_policy.py` from `icl-common-infra` over
every commit in a push or pull request, over the pull request text, and over the
committed files. To run it locally, use a checkout of `icl-common-infra`:

```bash
python3 path/to/icl-common-infra/scripts/check_text_policy.py commits origin/develop..HEAD
```
## Changelog fragments

Never edit `CHANGELOG.md` for an unreleased change. Add
`changelog.d/<slug>.<category>.md` with a category of `added`, `changed`,
`deprecated`, `removed`, `fixed` or `security`:

```markdown
Added `split` links that fan a single device out to several virtual ports.
```

```bash
python tools/changelog.py --check
python tools/changelog.py --dry-run
```

## Style

* C++23, four spaces, no tabs, `snake_case` for functions and types.
* Public headers are self-contained and documented with `///` comments.
* Prefer `vss::result<T>` over exceptions on API boundaries.
* Constrain templates with concepts (`vss::EventSink` is the pattern) so a
  misuse names the offending handler rather than the `std::function` machinery.
* No global mutable state; the hub and the studio own what they need.
* Tests are deterministic: wait for a condition, never assume a sleep is long
  enough.

## Threading rules

The rules in [docs/architecture.md](docs/architecture.md) are not style advice;
they are correctness. In particular:

* transports complete on the handler's associated executor,
* sinks capture state that outlives the hub,
* shutdown closes transports on their own strand.

Changes that touch `endpoint`, `hub` or a transport should be run against the
repeated system tests (`vss_system_tests --repeat=10`) before they are merged.

## Branch model

Development happens on **`develop`**, which is the trunk and the default
branch. Feature work branches from `develop` and merges back into it; `main`
is the release branch and only receives merges from `develop` when a release
is cut. That keeps `main` stable for users and gives releases an obvious
trigger.

```text
feature/* ──► develop ──► (release) ──► main
                 ▲
            day-to-day work
```

CI runs on pushes to `develop` and `main` and on every pull request. The
commit-authorship and changelog checks run everywhere.

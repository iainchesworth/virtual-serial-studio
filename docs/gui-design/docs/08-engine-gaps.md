# 08 Engine gap analysis and the backend adapter

The designs ask for some things the engine may not expose yet. **This table is built from the project's README and docs. I could not read the source, so treat "Known" as "documented" and verify every row in WP0.** Never change `vss_core` semantics to suit the GUI without an explicit task. Prefer a thin addition in `vss_studio`, and say so in the PR.

## The adapter rule
Put one narrow interface between the GUI and the engine, for example `StudioBackend` (name it after WP0 finds the existing conventions), with a `Capabilities` struct of booleans. Screens call the adapter, never the engine directly. Each feature checks its capability and, when absent, degrades visibly (disabled with a tooltip "Not available in this build", or a simpler variant) instead of failing or faking it.

## Capability table
| Capability the UI needs | Status | Plan if missing |
|---|---|---|
| Create, list, remove virtual ports (auto, pty, loopback, windows-driver) | Known | Use directly. |
| Enumerate serial devices and com0com pairs | Known (`vss_cli devices`) | Use directly. |
| Links: connect, split, join, redirect, monitor, merge policy interleave or owner | Known | Use directly. |
| Owner arbitration: set owner, release owner | Known (`set_owner`, `release_owner` on the hub) | Verify the studio facade exposes it. |
| **Shared bus link** (several ports on one wire, each hears all the others) | Provided by `vss_core` (`link_mode::bus`, `hub::bus`) and `vss::studio::bus`; `"mode": "bus"` with `members` in the JSON | The engine backend sets `Capabilities::shared_bus`. A backend without it keeps the star (a split from the master with a join tap): the Connect dialog shows "Shared bus" disabled with the tooltip "Not available in this build", the JSON editor says "Bus links are not available in this build" for a file that has one, and nothing simulates a bus out of other links. A bus has no modem lines and no owner, so the Line wiring and Owner tools skip it. |
| Cycle refusal on add link | Known (engine refuses) | Map the error to the loop pattern. "Show the loop" computes the cycle from the link graph in the GUI. |
| Events, counters, bounded traffic ring buffer | Known | Subscribe through the sink, marshal to the GUI thread, batch by refresh interval. |
| Set DTR, RTS, BREAK. Read CTS, DSR, DCD, RI | Known | Use directly. Unsupported lines return an error, show a disabled control. |
| Null-modem crossing with an on or off switch (`emulate_modem_lines`) | Known | Use for "Emulate modem lines". |
| **Per-link line wiring matrix** | Provided by `vss_core` (`modem_wiring` in `link_options`, `hub::set_link_wiring`) | The engine backend sets `Capabilities::line_matrix` and the matrix is editable. A backend without it shows the Standard preset read-only. The wiring is not saved in the topology JSON. |
| **Link delay and jitter** | Provided by `vss_core` (`delay_ms` and `jitter_ms` in `link_options`) and the topology JSON (`delay_ms`, `jitter_ms` on any link, a bus included) | The window has no control for it yet: it is set in the JSON editor or a topology file, and the Advanced JSON check places a bad value on its line. A link with a delay keeps it through save and open.|
| **Fixture sends, echo and a byte generator** | `endpoint::write` on a mock hands bytes to the device, which only records them. Sending *from* a fixture needs the mock's receive path. The scripted device (`vss::responder`) matches bytes that arrive on a port and replies fixed bytes, so it cannot echo a fixture, count or randomise. | `vss::studio::inject_data` (thin forwarding, like `inject_fault`) makes a fixture speak: `EngineStudioBackend::send` uses it for a mock. `vss::studio::set_fixture_echo` sends back every byte written to a fixture. `Capabilities::fixture_echo` says the backend has it; without it Echo is disabled with "Not available in this build". The byte generator (text line, fixed pattern, counter, random bytes) is plain sends on a GUI timer, bound to the fixture, and needs no capability. A scripted device from a JSON script file is not exposed in the window yet. |
| Fault injection on mock fixtures | Library mock backend can inject faults, GUI exposure unknown | Check the API on the object returned by `create_mock_port`. If absent, add a thin forwarding method in `vss_studio`. |
| **Peer-open detection** ("Waiting for program", "Program connected") | Provided for a pseudo terminal on Linux (`vss::peer_open`, `studio::peer_states`); unknown for everything else | Add a tri-state `PeerState` (Unknown, NotOpen, Open) to the adapter. "Open" is the normal state. Show "Waiting for program" and "Program connected" only where the adapter reports a definite NotOpen or Open (`Capabilities::peer_open`, a driver-side signal later), and say nothing about an outside program on Unknown. Never claim what you cannot know. |
| Setup check inputs (com0com present, elevation, dialout membership) | Partly known (`detect_com0com`, pair list work without elevation) | Small platform helpers in the GUI layer. |
| "Install com0com" and "Restart as administrator" | GUI actions | Never install silently. Install opens an instructions dialog with a button to open the project page (URL in one named constant, confirm with the maintainer). Restart as administrator relaunches the app elevated on Windows only. |
| **Elevation and operating-system protections** (UAC, Windows Firewall; Linux serial access, confinement and firewall; macOS firewall, Local Network and sandbox) | **Provided by `vss_ports`** (`vss/ports/permissions.hpp`) | `facts` with a reason code, an honest `unknown` where the platform cannot be asked, and one elevated step: the Windows Firewall rule for a listener, made by `vss_cli permissions firewall-allow` after the user agrees. `capabilities::firewall_rule` and `capabilities::serial_group_step` (the Linux polkit group step) say whether the build has the step; without it the dialog explains and shows the command, with "Not available in this build". Studio never elevates, changes a rule or a setting, or turns a protection off without that button. |
| Free com0com pair count for the share wizard | Partial | `com0com_installation.pairs` plus paths already claimed by `endpoint_infos` | Derive from the pair list and which ends the hub already claimed. WP6 derives it from the device list and the ports snapshot; no new engine API. |
| Create one more com0com pair from the share wizard | Partial | `vss::create_com0com_pair` exists, but `vss::studio` has no facade and the call needs elevation | WP6 adds `StudioBackend::create_com0com_pair()` in the GUI adapter (no library change), gated by `capabilities::com0com_pair_creation`. |
| Share as one operation with rollback | Known (share scenario, failed bridge rolls back) | Use directly. |
| Bridge by URI (`tcp://`, `udp://`, `rfc2217://`), client role | Known | Build the URI in the GUI, preview it, pass it through. |
| **Network bridge in the server role** (listen for other computers) | **Provided by `vss_ports`** (was missing in Boost.VirtualSerial) | Boost.VirtualSerial's `tcp_bridge_port` and `udp_bridge_port` only resolve and connect. `vss_ports` adds `listen_transport`, which `vss::studio::attach_serial` opens for `tcp-listen://host:port` and `udp-listen://host:port`; the GUI's server role builds those URIs. `capabilities::network_server` is true for the engine backend. A backend without it keeps the old behaviour: the dialog defaults to the client role and the server option is disabled with "Not available in this build". `rfc2217-listen://host:port` is the RFC 2217 access server (Telnet with the COM-PORT option); see `design-deviations.md`. Never simulate a listener. |
| JSON topology load, save, validate | Known (`vss_config`) | Use directly. |
| JSON validation errors with line and column | Unknown | Use `QJsonDocument::fromJson` offsets for syntax. For schema errors without positions, show the message and hide "Go to line". |
| Rename port | Provided by `vss_studio` (`studio::rename_port`) | The studio renames the endpoint, its records and a pseudo terminal's stable link together. `capabilities::rename_port` is true for the engine backend. A backend without it hides the menu item and F2. |
| Undo and redo | Not in the engine; a snapshot restore is not exact | The GUI keeps a history of changes with an exact inverse (connect and remove a link, change an owner) and clears it when the set of ports changes. No snapshot is restored and there is no Undo toast; confirmations stay. |
| Benchmark | CLI only (`vss_cli bench`) | Extract the core into a shared library function with progress and cancel callbacks, used by both CLI and GUI. Needs maintainer approval, do it in its own PR. |
| Diagnostic bundle zip | None | No new dependency. Write a small stored (uncompressed) ZIP writer in the GUI layer, with tests. |
| Event log tab | None | GUI-side `EventLog` fed from hub events. |
| Recent files, templates | None | `QSettings` list, and JSON templates bundled as Qt resources validated by `vss_config`. |
| Node positions in topology | Not in JSON | Session only. Do not change the JSON schema. |
